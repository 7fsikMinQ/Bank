# 서버 개선 제안 초안 (이사님 승인 후에만 적용, 한 번도 실행해 보지 않은 초안)

적용하지 마세요. 아래는 운영 서버에서 확인한 사실(톰캣 `/home/tomcat`, `startup.sh`, DB `mariadb.service`, 백업 스크립트)에 맞춰 쓴 초안이며 **시험되지 않았습니다.** 적용 전에 점검 시간대에 시작·종료 시험과 재부팅 시험을 해야 합니다.

## 1. 톰캣 자동 시작 (systemd 서비스)

배경: 11/6 재부팅 후 톰캣이 자동으로 올라오지 않아 약 9시간 중단되었습니다. DB는 `mariadb.service`가 enabled라 자동으로 올라왔습니다.

파일 위치(안): `/etc/systemd/system/tomcat.service`

```ini
[Unit]
Description=Apache Tomcat 8.5 (KIGTE)
After=network-online.target mariadb.service
Wants=network-online.target mariadb.service

[Service]
Type=forking
Environment=CATALINA_HOME=/home/tomcat
Environment=CATALINA_BASE=/home/tomcat
Environment=CATALINA_PID=/home/tomcat/temp/tomcat.pid
Environment=JRE_HOME=/usr
PIDFile=/home/tomcat/temp/tomcat.pid
ExecStart=/home/tomcat/bin/startup.sh
SuccessExitStatus=143
TimeoutStopSec=60

[Install]
WantedBy=multi-user.target
```

설명과 주의:

- 종료 명령(`ExecStop`)을 일부러 뺐습니다. 11/6 기동 직후 8005(종료 포트)가 열려 있지 않았고 사유는 확인하지 못했습니다. systemd가 보내는 종료 신호로 정상 종료되며, 11/6 00:43 종료도 같은 방식으로 정상 처리됐습니다.
- 서비스로 등록하면 `sh startup.sh`와 `sh shutdown.sh`를 병행하면 안 됩니다. 이미 서비스가 켜져 있는데 직접 기동하면 80/443 포트가 충돌합니다. 배포 절차가 `systemctl restart tomcat`으로 바뀌므로 담당자 합의가 필요합니다.
- 현재 톰캣은 사람이 띄운 프로세스입니다. 서비스 전환 때는 먼저 기존 프로세스를 종료한 뒤 서비스로 시작해야 합니다(서비스 중단이 생기므로 점검 시간에).

시험 절차(안, 점검 시간에):

1. 서비스 파일 생성 후 인식시키기: `systemctl daemon-reload`
2. 기존 톰캣 종료 → `systemctl start tomcat` → `catalina.out`에서 `Server startup` 확인, 80/443 확인, 브라우저 접속 확인
3. `systemctl stop tomcat` → 종료 로그 확인 → 다시 start
4. `systemctl enable tomcat`
5. 재부팅 시험(서비스 영향이 없는 시간) 후 톰캣이 자동으로 올라오는지 확인
6. 문제가 생기면 `systemctl disable tomcat`과 서비스 파일 삭제 후 기존 방식(`sh startup.sh`)으로 복귀

## 2. DB 백업 스크립트 개선

현재(`/root/script/db_backup.sh`, cron 매일 02:00)의 문제:

1. 덤프가 실패해도 어제 백업을 삭제함(성공 확인 없음)
2. 보관이 사실상 1일치
3. 같은 서버, 같은 디스크(DB 40G + 백업 40G, 여유 47G)
4. 비밀번호가 스크립트와 실행 중 프로세스 목록에 평문
5. `--single-transaction`, `--hex-blob`이 보이지 않음(첨부 longblob 복원 검증 필요)
6. 복원 시험 이력 [미확인]

개선 초안:

```bash
#!/bin/bash
BACKUP_DIR=/home/db_backup
DATE=$(date +%Y%m%d)
OUT="$BACKUP_DIR/kigte-backup_${DATE}.sql"
TMP="$OUT.tmp"

# 비밀번호는 권한 600인 옵션 파일로 분리 (명령줄 노출 방지)
if mariadb-dump --defaults-extra-file=/root/.backup.cnf \
     --single-transaction --hex-blob --max-allowed-packet=1G kigte > "$TMP" \
   && tail -n 1 "$TMP" | grep -q "Dump completed"; then
  mv "$TMP" "$OUT"
  find "$BACKUP_DIR" -type f -name 'kigte-backup_*.sql' -mtime +7 -delete
else
  rm -f "$TMP"
  echo "$(date) backup failed" >> /var/log/db_backup.log
fi
```

적용 전에 필요한 것:

- 디스크 여유 확인과 7일치 용량 계산: 현재 덤프 40G를 7일 보관하면 약 280G라 **지금 디스크(여유 47G)로는 불가능**합니다. 압축(압축률은 시험해야 앎), 보관 일수 축소, 디스크 증설, 외부 저장소 복사 중 선택해야 합니다.
- 복원 시험: 운영 백업을 서버 밖으로 가져가는 것은 실제 데이터를 옮기는 일이라 별도 승인이 필요합니다.
- 디스크 사용률 경보(예: 80% 초과) 설정
- 이 초안은 한 번도 실행해 보지 않았습니다.

## 3. 별도 안건으로 보고할 때의 요점

- 중단 보고 메일에는 넣지 않고, 별도 메일로 "백업 구조와 디스크 여유" 안건을 올립니다.
- 사실(확인됨): 백업 40G 단일 파일 / 어제 파일 삭제 구조 / 같은 디스크 / 여유 47G / DB 40G
- 계산(추정): 다음 02시 피크에 여유 약 7G. 증가 속도는 기록이 없어 알 수 없음. 내일 이후 `ls -lh /home/db_backup/`와 `df -h /` 값을 며칠 기록하면 하루 증가량을 알 수 있습니다.
